# 决策记录（ADR）

> 这份文档记录「为什么是现在这样」。很多看似可以简化的地方，背后都有一次踩坑。
> **修改任何一条之前，先读对应的「后果」和「验证」。** 新决定请追加，不要删旧条目。

格式：背景 → 决定 → 后果 → 验证方式。

---

## ADR-001 上游协议探测：chat 优先，超时不再回落 responses

- **日期**：2026-10
- **背景**：`auto` 模式需要判断上游支持 chat/completions 还是 responses。早期实现是「chat 失败（含超时）就试 responses」，结果一个**慢但健康**的中转（单次请求 15 s+）会被判成 `responses`，而 `/v1/messages` 当时只会把 chat 请求体发到 `/responses`，导致该实例所有真实请求 400/502。
- **决定**：
  1. chat 返回 200 且响应里有真实内容 → `chat_completions`；
  2. chat **超时或连接失败** → 直接返回 `chat_completions`（未知不等于不支持）；
  3. 只有 chat 明确失败（非 200 且有响应）才尝试 responses。
- **后果**：真正只支持 responses 且 chat 会超时的上游不会被自动识别，需要手动选择协议。这是有意的取舍：误判的代价（整站不可用）远大于漏判（手动点一下）。
- **验证**：`tests/test_profile_store.py::TestDetectUpstreamFormat::test_chat_timeout_keeps_chat_and_skips_the_second_probe`

## ADR-002 不做隐式重试

- **日期**：2026-10
- **背景**：用户遇到过 Claude Code 显示 `Waiting for API response · will retry in 4m 27s`，怀疑代理层是否需要自动重试。
- **决定**：代理**不**替客户端重试任何请求。重试策略属于 Claude Code / SDK；代理只做协议转换。
- **后果**：上游偶发失败会直接返回给客户端，由客户端决定重试。换来的是：不会重复计费、不会把非幂等请求执行两次、排障时错误来源清晰。
- **验证**：代码中不存在自动重试循环；400 学习（见 ADR-003）只影响**后续**请求，不重放当前请求。

## ADR-003 思考历史回传策略：规则 + 400 学习 + 探测，失败不落盘

- **日期**：2026-10
- **背景**：不同厂商对「历史 assistant 推理要不要回传」要求相反（R1 拒绝、DeepSeek V4/Kimi 要求工具轮回传），猜错直接 400。
- **决定**：
  - 六种模式：`auto`（规则 + 从 400 学习）/ `upstream`（启动时真实探测）/ `rules` / `turn` / `keep` / `drop`；
  - `turn` 指**当前轮**：最后一次真实用户输入之后的全部 assistant 消息（含多步工具调用）；
  - 学习结果按 `base_url + model` 指纹持久化，改配置自动失效；
  - **探测失败（超时/无信号/鉴权失败）绝不写纠正**，只提示「未得出结论」；
  - 探测总预算 20 s，两个探测请求并发。
- **后果**：`auto` 模式默认零额外请求；`upstream` 模式的启动探测在**后台线程**跑，不阻塞端口开放。
- **验证**：`tests/test_thinking_policy.py`（含 400 学习、指纹失效、失败不落盘、并发预算）。

## ADR-004 新增「上游只支持 Responses」的适配层

- **日期**：2026-10-29
- **背景**：`upstream_format=responses` 以前只改 URL、不改请求体：chat 格式的 body 被发到 `/responses`，上游直接 400。
- **决定**：新增 `upstream_responses.py`，把内部统一的 Chat 请求体转成 Responses（`input`/`tools`/`reasoning`），把响应与 SSE 再转回 Chat。`/v1/responses` 在上下游同为 Responses 时**直接透传**，不做有损往返。
- **后果**：三条入口（`/v1/messages`、`/v1/chat/completions`、`/v1/responses`）都能对接 Responses 上游。新增了一条需要同时维护的转换路径。
- **验证**：`tests/test_upstream_responses.py`；真实上游实测覆盖文本、流式、工具调用、多轮工具历史。

## ADR-005 事件循环里不做阻塞 IO

- **日期**：2026-10-29
- **背景**：Manager 启动时串行自启 7 个实例，期间 `netstat`/`taskkill`/`tasklist` 同步调用阻塞事件循环，导致面板请求和探测请求排队 20 s 以上、探测被误判为超时。
- **决定**：
  - 一切 shell 调用（`_find_pid_by_port`、`_process_name`、`_terminate_pid`、`proc.wait`）走 `asyncio.to_thread`；
  - 端口总览/端口自检路由整体丢线程；
  - 实例自启改为 `asyncio.gather` 并发；
  - Worker 启动时的思考策略探测放后台线程。
- **后果**：重启后面板 ~10 s 可用、全部实例 ~35 s 就绪（原先 1–2 分钟）。
- **验证**：`supervisor.py` 中不得再出现裸 `subprocess.run` 在 `async def` 内；实测 `ccconvert restart` + 并发请求。

## ADR-006 进程树终止 + 父进程看门狗

- **日期**：2026-10-29
- **背景**：Windows 下 `taskkill /F` 只杀启动器外壳，真正的 Worker 继续占用端口，下次启动报 `WinError 10048`。强停 Manager 也会留下孤儿 Worker。
- **决定**：
  1. `taskkill /F /T`（`supervisor._terminate_pid` 与 `daemon._force_kill`）；
  2. 启动前同时检查 pid 文件与 meta 文件里的 PID，两者都驱逐；
  3. Worker 在后台线程监视 Manager PID，Manager 消失 2 s 内自行退出。
- **后果**：`stop -f` 后没有残留 Worker；端口冲突只可能来自外部进程。
- **验证**：实测 `stop -f` 后无 `worker_runner.py` 进程；`tests/test_daemon_advanced.py` 断言 `/T` 参数。

## ADR-007 配置与运行时路径统一走 `runtime_paths`

- **日期**：2026-10
- **背景**：`profile_store` 曾自己读取一个**名字带空格**的环境变量（`"CC Convert_CONFIG_DIR"`），导致文档承诺的目录覆盖长期失效、测试污染真实配置。
- **决定**：所有路径只允许通过 `runtime_paths`（`get_config_dir` / `get_runtime_dir` / `get_log_dir` / `get_instance_dir`）获取；不要在别处另写解析。
- **后果**：`CCCONVERT_CONFIG_DIR` / `CCCONVERT_RUNTIME_DIR` 真正生效，测试可在模块级沙箱。
- **验证**：`tests/conftest.py` 的沙箱 + 真实配置绊线；全仓库搜索不得出现硬编码路径。

## ADR-008 密钥：stdin 传给 Worker，但面板可展开

- **日期**：2026-10
- **背景**：上游 key 不能出现在命令行/环境变量/日志里；同时用户明确要求编辑页能看到完整密钥（否则无法确认配置是否正确）。
- **决定**：
  - Manager → Worker 通过 **stdin JSON** 传递 key；
  - Dashboard 提供 `GET /api/instances/{id}/key` 返回完整 key，仅本机可访问（面板只绑 localhost + CSRF）；
  - 日志与错误信息不得包含 key。
- **后果**：面板暴露 key 是有意的本地便利；把面板暴露到公网等于泄露 key。
- **验证**：`worker_runner.py` 读 stdin；日志检查；`tests/test_manager_routes.py`。

## ADR-009 测试沙箱与「真实配置绊线」

- **日期**：2026-10
- **背景**：一次测试把用户真实的 `~/.ccconvert/config.toml` 原子覆盖了。
- **决定**：
  - `tests/conftest.py` 在**模块级**设置 `CCCONVERT_CONFIG_DIR` / `CCCONVERT_RUNTIME_DIR`（不能放 fixture：`daemon.py` 导入时就固化了路径）；
  - 会话结束比对真实配置的 `(mtime, size)`，变了就让测试失败；
  - 每个用例重置环境变量，防止 `patch.dict(clear=True)` 泄漏出沙箱。
- **后果**：跑测试永远不会碰真实配置；泄漏会立刻变红。
- **验证**：`tests/conftest.py` 本身；`uv run pytest` 后 `~/.ccconvert/config.toml` 不变。

## ADR-010 用量统计：价格带版本，成本两种口径

- **日期**：2026-10-29（设计，未实现）
- **背景**：需要同时回答「我实际花了多少」和「如果换成另一家/另一个倍率会花多少」。
- **决定**：
  - 价格表带 `effective_from`，改价 = 追加新版本；
  - 默认「按当时价」计费，另提供「按现价」开关用于模拟；
  - 存储只存 token 与上下文档位，不存单价。
- **后果**：改价不会污染历史账单；模拟换站无需导入导出。
- **验证**：见 `docs/用量统计实施计划.md` 的验收项。

## ADR-011 缓存 TTL：以实例设置为准，请求侧只作提示

- **日期**：2026-10-29（设计，未实现）
- **背景**：OpenAI 兼容中转不返回缓存 TTL 拆分；转成 OpenAI 协议时 `cache_control` 也不会继续传给上游，实际 TTL 由中转决定。
- **决定**：
  1. 上游返回拆分（Anthropic 原生）→ 精确使用；
  2. 否则用**实例设置**的「上游缓存 TTL」（默认 5m）计费；
  3. 请求里的 `cache_control.ttl` 只在面板标注「客户端请求了 1h」，**不参与计费**；
  4. 估算标记 `cache_write_est`，不把猜测当事实。
- **后果**：需要用户为每个中转设一次 TTL；不设也不会错得离谱（默认 5m 是最常见的）。
- **验证**：见实施计划的计费用例。

## ADR-012 服务端搜索不用于「Responses 原生上游」路径

- **日期**：2026-10-29
- **背景**：`/v1/responses` 在上下游同为 Responses 时走直通；一旦请求里带 `web_search` 工具，旧代码会落回「转成 chat + 本地搜索循环」，而该循环只会说 chat/completions，最终把 chat 请求体发到 `/responses`，必然 400。
- **决定**：上游是 Responses 时**一律直通**，包括带 `web_search` 的请求；工具原样交给上游。本地 Tavily/通晓 只用于 chat 上游。
- **后果**：Responses 上游用户无法使用本地的搜索 provider（但可以用上游自带的 web_search）。代码里保留一条 WARNING 说明。
- **验证**：`tests/test_incident_fixes.py::TestResponsesUpstreamDefects::test_responses_endpoint_passes_through_when_web_search_is_present`

## ADR-013 用量统计采集：单库多 Worker、内存台账、诚实计数

- **日期**：2026-10-30（已实现，P0/P1）
- **背景**：需要回答「各中转/各模型用了多少 token、缓存率多少」。中转不统一返回 usage，
  且三种入口（Anthropic / Chat / Responses）对 `input_tokens` 的缓存语义相反。
- **决定**：
  1. 存储用**一个共享 SQLite**（`<runtime>/usage.db`，WAL + busy_timeout）：Worker 各写自己的
     `instance_id` 行，主键天然不冲突；不用 JSON/JSONL（无法按任意范围聚合）。
  2. 请求线程只做**内存字典累加**（15 分钟桶），后台线程每 5 s 批量 upsert，进程退出再刷一次；
     flush 失败只 WARNING，绝不影响代理。强杀最多丢 5 s 统计，可接受。
  3. **诚实计数**：拿不到 usage 记 `unreported`，不按 0、不做估算；台账里 `cache_write_est`
     标记 TTL 依赖配置假设的部分（见 ADR-011）。
  4. 流式用 `recorder.latest()`（多次上报取最后一次），服务端工具循环用 `recorder.upstream()`
     （逐次累加），`finish()` 统一入账——见不变量 A4。
  5. chat 透传流注入 `include_usage` 拿 usage；客户端没要求时把 usage chunk 剥离，
     客户端可见流不变（见不变量 A6）。
  6. Manager 只读不建库（见不变量 D4）；`/_ccconvert/status` 只新增 `usage` 字段。
- **后果**：所有代理路径都要接 recorder（采集矩阵见实施计划 §4），新增上游调用路径漏接
  就会静默少记账；SQLite 成为第 4 个运行时文件。
- **验证**：`tests/usage/`（归一化/台账/存储/集成 64 例）；实机验收：对 gguuai 发流式、
  非流式、chat 透传请求，库中数字与上游返回一致。

## 追加新 ADR 的规则

1. 一个决定一条，编号递增；
2. 必须写「如果不这样做会怎样」（后果）；
3. 必须写「怎么验证」——能落成测试的优先落成测试；
4. 推翻旧决定时，旧条目标记 `已被 ADR-xxx 取代`，不要删除。
