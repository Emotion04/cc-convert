# 架构总览

> 目标：读完能在脑内跑通一次请求，知道每个文件负责什么、改哪里会碰到什么。
> 细则见 [不变量与陷阱](不变量与陷阱.md)；设计取舍见 [决策记录](决策记录.md)。

## 1. 这是什么

CC Convert 是一个**本地协议桥**：让 Claude Code（Anthropic Messages API）以及 OpenAI SDK 客户端，可以跑在任意 OpenAI 兼容上游（中转站、vLLM、SGLang、云 API）上。

```
Claude Code ──Anthropic /v1/messages──▶ Worker(实例端口) ──Chat / Responses──▶ 上游
OpenAI SDK  ──Chat/Responses──────────▶ Worker(实例端口) ──Chat / Responses──▶ 上游
```

它不做模型推理，只做四件事：**协议转换、实例管理、进程生命周期、诊断**。

## 2. 进程模型

```
┌─────────────────────────────────────────────────────────────┐
│ Manager 进程（ccconvert start 启动的后台守护进程）            │
│  ├─ FastAPI Dashboard :18400+（只绑 localhost，CSRF 保护）    │
│  ├─ ProfileStore（~/.ccconvert/config.toml，唯一事实源）      │
│  └─ InstanceSupervisor（子进程管理 + 健康检查）               │
│        │ stdin JSON（含 API key）/ 健康轮询                   │
│        ▼                                                      │
│  ┌──────────────┐   ┌──────────────┐        ┌──────────────┐ │
│  │ Worker :18401│   │ Worker :18402│  ...   │ Worker :1840N│ │
│  │ 协议转换      │   │ 协议转换      │        │ 协议转换      │ │
│  └──────────────┘   └──────────────┘        └──────────────┘ │
└─────────────────────────────────────────────────────────────┘
```

关键点：

- **Manager 和 Worker 是两个独立进程**，Worker 崩溃不影响其他实例；Manager 重启会重建 Worker（见 §6）。
- Worker 的配置通过 **stdin 的一行 JSON** 传入：`instance_id`、`internal_token`、`revision`、`settings_kwargs`、`host`、`port`、`parent_pid`。key 在其中，不走 argv/env。
- Worker 监听 `127.0.0.1:<实例端口>`，Dashboard 监听 Manager 端口（默认 18400，被占用时向上扫描且避开所有实例端口）。**Claude Code 必须连实例端口，不是 Manager 端口**（最常见的误配置）。
- Worker 由 Manager 的 Supervisor 启动，并在后台线程监视 Manager PID：Manager 消失后 2 s 内自行退出（防止孤儿进程占端口）。
- 健康检查：`GET /_ccconvert/status` + `Bearer <internal_token>`，60 次 × 200 ms（约 12 s）；必须同时匹配 `instance_id` 与 `revision`。
- Manager 的 Dashboard 页面里必须保留字符串 `CC Convert Manager`（`daemon.py::_MANAGER_MARKER`）：停止一个「端口被占但 PID 文件丢失」的 Manager 时，会先 GET `/` 校验这个标记，避免误杀别人的进程。
- `Settings` 的注释声称忽略环境变量，但 `BaseSettings` 默认 env source 仍生效（见 `不变量与陷阱` I8）。

## 3. 一次请求的完整路径（`/v1/messages`）

```
1. Worker 收到 POST /v1/messages（Anthropic 格式）
2. get_request_settings()            # 该实例的 Settings（config.py）
3. 解析 + 校验 body（protocol.py）
4. settings.resolve_model(model)      # 精确映射 → fnmatch → target_model → 透传
5. convert_anthropic_to_openai(...)   # converter.py
      ├─ system / messages / tools / tool_choice / thinking
      ├─ 历史推理块按 thinking_history 策略过滤（thinking_policy.py）
      └─ 工具调用与 tool_result 对齐（_ensure_tool_results_for_tool_calls）
6. 如有服务端工具 → tools/handler.py 的循环（可能多次上游调用）
7. 目标 URL：_upstream_url(settings, "messages")
      chat_completions → {base}/chat/completions
      responses        → {base}/responses（请求体经 upstream_responses.py 转换）
8. 流式：_stream_response(...) 逐块转 Anthropic SSE
   非流式：POST → _to_chat(响应) → ChatCompletion 校验 → convert_openai_to_anthropic
9. 返回 Anthropic 消息 / SSE；usage 归一化
```

其它端点：`GET /v1/models`（原样代理上游）、`POST /v1/messages/count_tokens`（tiktoken 估算，不调上游）、`GET /health`、`POST /api/event_logging/batch`（Claude Code 的遥测占位，返回 204）。

三条入口共享同一套转换与上游调用约定：

| 入口 | 客户端格式 | 上游格式 | 请求转换 | 响应转换 |
|---|---|---|---|---|
| `/v1/messages` | Anthropic | Chat | `convert_anthropic_to_openai` | `convert_openai_to_anthropic` |
| `/v1/messages` | Anthropic | Responses | 上面 + `chat_body_to_responses_body` | `responses_payload_to_chat_completion` + 上面 |
| `/v1/chat/completions` | Chat | Chat | 无（透传） | 无 |
| `/v1/chat/completions` | Chat | Responses | `chat_body_to_responses_body` | `responses_payload_to_chat_completion` |
| `/v1/responses` | Responses | Chat | `convert_responses_to_chat_completion` | `convert_chat_completion_to_responses` |
| `/v1/responses` | Responses | Responses | **直通** | **直通** |

流式的两个关键函数：

- `streaming/handler.py::_stream_response` 只认 **Chat SSE**。
- 上游是 Responses 时，`upstream_responses.responses_sse_as_chat_sse` 先把 Responses 事件翻译成 Chat chunk，再交给上面那个函数——所以 Anthropic 事件生成逻辑只有一份。

## 5. 配置与路径

| 内容 | 位置 | 覆盖方式 |
|---|---|---|
| 实例配置 | `~/.ccconvert/config.toml` | `CCCONVERT_CONFIG_DIR` |
| 运行时（pid/meta/日志/实例目录） | `%LOCALAPPDATA%\ccconvert` / `~/.local/share/ccconvert` | `CCCONVERT_RUNTIME_DIR` |
| 每个实例的日志 | `<runtime>/instances/<id>/logs/{server,api}.log` | — |

- schema v2，v1 自动迁移；`ProfileStore` 是配置的唯一事实源。
- Dashboard 是推荐的编辑方式；Manager 运行时手改 TOML 会被内存中的 store 覆盖。

## 6. 生命周期

### 启动

1. `ccconvert start` → `daemon.py` fork 出 Manager 进程（`daemon_runner.py`）。
2. Manager 加载 ProfileStore、生成 CSRF token、绑定端口。
3. `lifespan` 里用**后台任务**执行 `supervisor.startup_all()`，Dashboard 立即可用。
4. `startup_all` **并发**启动每个 `auto_start` 实例。
5. 每个实例：驱逐残留进程（pid/meta 双来源 + 进程树）→ 校验端口 → spawn → stdin 传配置 → 轮询健康检查。

### 停止 / 重启

- 正常停止：Supervisor 逐个 terminate 并等待；Worker 收到信号后删 pid 文件退出。
- 强制停止：`taskkill /F /T` 杀掉 Manager 进程树；即使漏网，Worker 的父进程看门狗也会在 2 s 内退出。
- 重启 = 停止 + 启动；配置变更通过 `supervisor.update_instance` 原地重启对应 Worker。

### 崩溃恢复

- Worker 提前退出：健康轮询检测到 `proc.poll() is not None`，记录 stderr 尾部并返回失败。
- 端口被占：先按 pid 文件/meta 驱逐，再按端口找占用者（netstat + PowerShell 兜底）。
- 更新配置失败：回滚到旧配置并尝试重启（`update_instance`）。

## 7. Dashboard

页面：`/`（实例）、`/config`（新建/编辑）、`/ports`（端口诊断）、`/logs`、`/api-test`、`/docs`。

- 所有页面共用 `base.html`（Tailwind + Alpine.js）。
- 变更请求必须带 `X-CCCONVERT-CSRF`；Manager 每次启动换 token。
- 常用 API：实例 CRUD、启停、`/api/instances/{id}/key`（明文 key）、`/api/probe-thinking`、`/api/detect-format`、`/api/ports/*`、`/api/global`。

## 8. 扩展点（新增功能往哪放）

| 想加 | 放哪 | 注意 |
