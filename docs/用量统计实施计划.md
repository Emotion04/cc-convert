# Token 用量统计：实施计划

> 设计见 `docs/用量统计设计.md`，决策见 `docs/决策记录.md` ADR-010/011。
> 本文是可执行的任务分解：每个阶段独立可验收、可提交，失败可回滚。

## 0. 目标（Definition of Done）

1. 面板能看到**任意时间范围**（今天 / 7 / 30 / 90 / 180 天 / 自定义）的：
   输入、输出、缓存读、缓存写、缓存率、请求数、估算成本。
2. 维度：按**实例（中转）**、按**模型**、按**规范模型**、按入口。
3. 同一规范模型在多个中转之间可对比：缓存率、每请求输出、每请求成本、有效倍率。
4. 价格可配置：标准价目表 + 站点倍率 + 模型映射 + 上下文档 + 时段规则 + 缓存 TTL。
5. 图表：折线（时间）、饼图（构成）、分组条形（对比）、散点（成本 vs 缓存率）。
6. 重启/停止实例不丢历史；不记录任何请求正文。
7. `uv run pytest` 全绿，新增模块覆盖率 > 90%。

## 1. 前置状态（开始前必须知道）

- 工作区可能有一批**未提交**的改动（Responses 上游适配、探测修复、孤儿进程修复）。开始新工作前先确认 `git status`，必要时先提交一个基线。
- `runtime_state.py` 目前只有请求计数，没有 token 台账。**不要**在它上面直接堆 UI 逻辑，按第 2 节拆分。
- 现有 `/_ccconvert/status` 被 Supervisor 用于健康检查，**必须保持向后兼容**（只加字段，不改已有字段/状态码）。

## 2. 模块划分（新增文件）

```
src/cc_convert/usage/
├── __init__.py
├── ledger.py        # 内存累加 + 15 分钟桶 + 上下文档位
├── store.py         # SQLite schema、upsert、聚合查询（只被 Manager/Worker 调）
├── recording.py     # 从三种 usage 形状归一化（anthropic/chat/responses）
└── pricing.py       # 价目表解析、版本选择、分档/时段/TTL、成本计算（纯函数，无 IO）
```

- `pricing.py` 必须是**纯函数**（输入 token + 时间 + 价格配置 → 成本），这样才能单测穷举。
- `store.py` 只做 SQL，不做业务判断。
- `recording.py` 不做 IO，Worker 调用后交给 `ledger`。

## 3. 阶段任务

### P0：采集与存储（1 个 PR）

**改动**

| 文件 | 改动 |
|---|---|
| `usage/ledger.py` | 新增：按 (15min, instance, model, client_model, endpoint, prompt_class) 累加；`flush()` 返回脏桶 |
| `usage/recording.py` | 新增三个归一化函数 + `prompt_class()` |
| `usage/store.py` | 新建 DB + schema + `upsert_buckets()` + `query()` |
| `runtime_state.py` | 注入口：`record_usage()` 转调 ledger；`to_dict()` 增加 `usage` 摘要 |
| `main.py` | 创建 ledger/store，启动后台 flush 线程；status 端点加 `usage` 字段 |
| `worker_runner.py` | 关闭时 flush；确保 DB 路径来自 `runtime_paths` |
| 采集点 | `router.py` 非流式/流式、`openai_chat_completions`、`_openai_stream_proxy`、`_proxy_responses_passthrough`、`tools/handler.py` 循环 |

**关键实现细节**

1. 采集点都要容错：拿不到 usage → `unreported += 1`，绝不按 0 记账。
2. 流式路径的 usage 只在结束块出现；`/v1/chat/completions` 透传时必须给上游加 `stream_options.include_usage`（当前只在转换路径加过，透传路径要确认）。
3. 服务端工具循环一次客户端请求可能打 N 次上游，**逐次记账**，最后一个 chunk 的 usage 也要算。
4. 写库在后台线程，5 s 批量；任何异常只记 WARNING，不影响请求。

**测试**

- `tests/usage/test_recording.py`：三种 usage 形状 → 归一化字段（含 cached 减法）。
- `tests/usage/test_ledger.py`：同桶累加、跨 15 分钟分桶、prompt_class 边界（31999/32000/199999/200000）。
- `tests/usage/test_store.py`：upsert 幂等、按范围查询、跨进程（两个连接）写入。
- 集成：用假上游返回固定 usage，发一次 `/v1/messages`（流式+非流式），断言库里恰好一行且数字一致。

**验收**：手工发 3 类请求后 `sqlite3 usage.db "select * from usage_bucket"` 与上游返回一致；重启后数据仍在。

### P1：总览面板（1 个 PR）

**后端**：`GET /api/usage/summary`（见设计文档 §8）。
**前端**：`/usage` 页面 + 侧边栏入口；vendored Chart.js。

页面结构：
- 顶部：时间范围（今天/7/30/90/180/自定义）+ 粒度（小时/天）+「按当时价/按现价」开关（P2 前禁用）。
- KPI 卡片：请求、输入、输出、缓存读、缓存写、缓存率、成本。
- 堆叠面积折线：四类 token 随时间。
- 环形图：所选范围构成。
- 分组条形：按实例 / 按模型切换。
- 明细表：可排序，含缓存率。

**验收**：切 7/30 天数字与 SQL 手算一致；空数据不报错；浏览器断网仍能渲染（图表本地加载）。

### P2：计费引擎（1 个 PR）

**改动**

| 文件 | 改动 |
|---|---|
| `usage/pricing.py` | 价目表版本选择（`effective_from <= bucket_ts`）、分档、时段、TTL、成本 |
| `usage/store.py` | `price_catalog` / `vendor_price` / `price_tier` / `price_time_rule` 的 CRUD |
| `web/routes.py` | `GET/PUT /api/usage/pricing` |
| `templates/usage_pricing.html` | 价目表 + 站点倍率 + 模型映射 + 分档/时段规则表单 |

**默认价目表**（可编辑，仅作种子）：至少包含当前在用的模型，以及 Claude / GPT / DeepSeek / Gemini 各一条示例。

**测试**：纯函数用例覆盖
- 基本乘法；
- 分档边界（199999 vs 200000）；
- 时段跨午夜、时区；
- 5m/1h 缓存写入分开计价；
- 「按当时价」在价格版本切换日的结果、「按现价」用最新版；
- 有效倍率计算。

**验收**：手工算一笔与面板一致；改倍率后默认口径历史不变、按现价口径变化。

### P3：对比页（1 个 PR）

`GET /api/usage/compare?catalog=...&from=&to=` + `/usage/compare` 页面：

- 选择规范模型 → 列出所有映射到它的实例；
- 指标：缓存率、每请求输入/输出、每请求成本、有效倍率；
- 图：分组条形（每请求成本）、多折线（每日缓存率）、散点（缓存率 vs 每请求成本，点大小=请求量）；
- 表格带 Δ%（相对最优/基线）。

**验收**：同一模型在两家中转的对比与手工报表一致；切换时间范围后排序合理。

### P4：高级定价 + 余额（可选）

- 上下文档自定义阈值（非标准值时显示近似提示）；
- 时段规则多段重叠的优先级（取最后命中/最小倍率——需在 UI 明示）；
- 余额探测适配器（one-api/new-api/OpenAI 预设 + 自定义 JSON 路径），失败静默；
- CSV 导出、日账单快照（若要「历史真实账单」不被改价影响）。

## 4. 数据采集矩阵（实现时逐项打勾）

| 路径 | 非流式 | 流式 | 服务端工具循环 |
|---|---|---|---|
| `/v1/messages`（chat 上游） | ☑ | ☑ | ☑ |
| `/v1/messages`（responses 上游） | ☑ | ☑ | ☑ |
| `/v1/chat/completions`（透传） | ☑ | ☑ | — |
| `/v1/responses`（chat 上游） | ☑ | ☑ | ☑ |
| `/v1/responses`（responses 直通） | ☑ | ☑ | — |

> 每一项都要有测试，否则很容易出现「面板数字比账单少」的静默 bug。
> P0 已实现（见 `tests/usage/`）；直通流的 usage 从 `response.completed` 事件提取；
> chat 透传流会给上游注入 `stream_options.include_usage`，但若客户端未主动要求，
> 该 usage chunk 会被剥离，客户端可见流保持不变。

## 5. 兼容与迁移

- `usage.db` 带 `schema_version`，启动时执行幂等 migration；未知版本拒绝写入并 WARNING（不要破坏已有数据）。
- 旧的 `usage.json` 台账（如果某版本存在）读入后合并一次再删除，避免重复计数。
- `/_ccconvert/status` 只加 `usage` 字段，不改已有字段。
- 面板与 API 都是新增，不改现有路由。

## 6. 性能预算

- 请求路径新增开销：一次字典累加 + 一次分类（纳秒级），**不得有 IO**。
- 后台 flush：每 5 s 一次事务；单实例 7 个模型时 < 5 ms。
- 查询：180 天范围在 70 万行内必须 < 200 ms；超过就加覆盖率索引或预聚合日表。

## 7. 回滚

- 所有新表/新路由都是增量；关闭面板入口即可回滚 UI。
- 采集失败只影响统计，不影响代理：上层异常必须被 `usage` 模块吞掉并 WARNING。
- 若 DB 文件损坏：删除 `usage.db` 即可重建，代理照常运行。

## 8. 提交边界

P0/P1/P2/P3 各自独立提交，便于 `git bisect`。P0 的采集点改动最接近热路径，必须单独提交并附集成测试。
