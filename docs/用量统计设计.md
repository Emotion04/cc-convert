# CC Convert 用量统计设计（Token / 缓存 / 成本 / 中转对比）

> 状态：设计稿，未实现。本文只回答「做什么、怎么存、怎么算、画什么图」，不含代码。

## 1. 需求拆解

从你的描述里提取出 6 组硬性需求，后面的所有设计都为它们服务：

| # | 需求 | 隐含的技术要求 |
|---|---|---|
| R1 | 保留全部数据，能查最近 7 天 / 30 天 / 半年 | 必须存**时间序列**，不能只存累计值 |
| R2 | 分配置（中转站）、分模型看 输入/输出/缓存读/缓存写/缓存率 | 每一条记录都要带 instance + model + 端点维度 |
| R3 | 同一个模型在两家中转的对比（缓存率、输出量、真实单价） | 需要「规范模型」概念，把两家的模型名映射到同一个标准 |
| R4 | 填入标准价 + 站点倍率，自动算钱，不用逐模型填价 | 价目表 与 站点倍率 分离，成本 = 标准价 × 倍率 |
| R5 | 上下文分档、时段折扣、缓存 5 分钟/1 小时不同价 | 计费要能看到「本次请求的上下文长度」和「时间」 |
| R6 | 可视化：饼图 / 条形图 / 折线图，必要时对比 | 前端图表库 + 聚合接口 |

**非目标（本期不做）**：记录请求/响应正文、会话级追踪（magpie 的 sessions）、OTLP 导出、多用户。

## 2. 数据从哪来

所有用量都来自上游返回的 `usage`。三条入口的形状不同，必须先归一化。

| 入口 | 上游形状 | 字段 |
|---|---|---|
| `/v1/messages` | Anthropic | `input_tokens`（**不含缓存**）、`output_tokens`、`cache_read_input_tokens`、`cache_creation_input_tokens` |
| `/v1/chat/completions` | OpenAI Chat | `prompt_tokens`（**含缓存**）、`completion_tokens`、`prompt_tokens_details.cached_tokens`、`completion_tokens_details.reasoning_tokens` |
| `/v1/responses` | Responses | `input_tokens`（**含缓存**）、`output_tokens`、`input_tokens_details.cached_tokens` / `cache_write_tokens` |

统一成一张表：

```
输入（未命中缓存） = Anthropic: input_tokens
                     Chat/Responses: prompt_tokens - cached_tokens
缓存读取           = cache_read_input_tokens / cached_tokens
缓存写入           = cache_creation_input_tokens / cache_write_tokens
缓存写入(1h)       = 若上游区分 TTL 才有，否则并入「5m/未知」
输出               = output_tokens / completion_tokens
推理输出           = reasoning_tokens（可选列，成本核算用）
```

**采集点**（漏一个就会出现「面板数字比账单少」）：

1. `/v1/messages` 非流式 —— 响应里的 `usage`
2. `/v1/messages` 流式 —— 结束时的 usage chunk（`stream_options.include_usage` 已开启，但中转可能不返回）
3. `/v1/chat/completions` 非流式 / 流式
4. `/v1/responses` 非流式 / 流式（直连 Responses 或经 chat 转换）
5. 服务端工具循环 —— **一次客户端请求会打好几次上游**，必须逐次累加

**诚实原则**：中转不返回 usage 时记 `unreported += 1`，面板显示「N 次请求未上报用量」，**绝不按 0 计**，也不虚构估算值。

## 3. 存储设计

### 3.1 选型：SQLite（Python 内置，无新依赖）

- 单文件 `%LOCALAPPDATA%\ccconvert\usage.db`（`runtime_paths` 提供路径）。
- WAL 模式 + `busy_timeout=5000`：多个 Worker 并发写、Manager 并发读都不会互相阻塞。
- 不用 JSON/JSONL：你需要「任意时间范围 + 多维聚合」，JSON 要么全量载入内存，要么自己写索引。

### 3.2 表结构

```sql
-- 15 分钟一个桶。时段折扣的边界通常是 :00 / :30，15 分钟粒度够用。
CREATE TABLE usage_bucket (
    ts            INTEGER NOT NULL,   -- epoch 秒，向下取整到 15 分钟
    instance_id   TEXT    NOT NULL,   -- 配置（中转实例）
    vendor        TEXT    NOT NULL,   -- 中转站名，默认 = 实例名，可多个实例同 vendor
    model         TEXT    NOT NULL,   -- 上游实际模型（解析后）
    client_model  TEXT    NOT NULL,   -- 客户端请求的模型名（映射前）
    endpoint      TEXT    NOT NULL,   -- /v1/messages | /v1/chat/completions | /v1/responses
    -- 本次请求的上下文规模档位。请求自己是知道自己有多长的
    -- （input + cache_read + cache_write），所以这里不需要近似。
    prompt_class  TEXT    NOT NULL,   -- 0-32k | 32-128k | 128-200k | 200-400k | 400k-1M | >=1M
    input_tokens  INTEGER NOT NULL DEFAULT 0,
    output_tokens INTEGER NOT NULL DEFAULT 0,
    reasoning_tokens INTEGER NOT NULL DEFAULT 0,
    cache_read    INTEGER NOT NULL DEFAULT 0,
    cache_write   INTEGER NOT NULL DEFAULT 0,   -- 5 分钟 TTL
    cache_write_1h INTEGER NOT NULL DEFAULT 0,  -- 1 小时 TTL
    -- TTL 归类依据：response（上游拆分）/ config（实例设置）/ request_hint（仅提示）
    ttl_source    TEXT    NOT NULL DEFAULT 'config',
    -- 依赖估算（非 response 来源）的缓存写入 token 数，面板打「估算」标记
    cache_write_est INTEGER NOT NULL DEFAULT 0,
    requests      INTEGER NOT NULL DEFAULT 0,
    errors        INTEGER NOT NULL DEFAULT 0,
    unreported    INTEGER NOT NULL DEFAULT 0,
    duration_ms   INTEGER NOT NULL DEFAULT 0,   -- 便于对比两家的「贵是否因为慢/输出多」
    PRIMARY KEY (ts, instance_id, model, client_model, endpoint, prompt_class)
) WITHOUT ROWID;

CREATE INDEX idx_usage_ts       ON usage_bucket(ts);
CREATE INDEX idx_usage_instance ON usage_bucket(instance_id, ts);
CREATE INDEX idx_usage_model    ON usage_bucket(model, ts);

-- 规范模型价目表（标准价，USD / 1M tokens）。
-- 价格带版本：改价 = 追加一行新的 effective_from，旧价格不动，
-- 这样「按当时价」的历史账单永远稳定，「按现价」则是最新一行。
CREATE TABLE price_catalog (
    id            TEXT NOT NULL,         -- claude-opus-5
    effective_from INTEGER NOT NULL,     -- epoch 秒，生效时间
    display_name  TEXT NOT NULL,
    input         REAL NOT NULL,         -- 未命中缓存输入
    output        REAL NOT NULL,
    cache_read    REAL NOT NULL DEFAULT 0,
    cache_write_5m REAL NOT NULL DEFAULT 0,
    cache_write_1h REAL NOT NULL DEFAULT 0,
    currency      TEXT NOT NULL DEFAULT 'USD',
    updated_at    INTEGER NOT NULL,
    PRIMARY KEY (id, effective_from)
);

-- 上下文分档：prompt_tokens 达到 min_prompt 后，各单价乘 mult
CREATE TABLE price_tier (
    catalog_id    TEXT NOT NULL,
    min_prompt    INTEGER NOT NULL,
    input_mult    REAL NOT NULL DEFAULT 1,
    output_mult   REAL NOT NULL DEFAULT 1,
    cache_read_mult REAL NOT NULL DEFAULT 1,
    cache_write_mult REAL NOT NULL DEFAULT 1,
    PRIMARY KEY (catalog_id, min_prompt)
);

-- 时段规则：按本地时区判断，命中则乘 mult（如 DeepSeek 夜间 5 折）
CREATE TABLE price_time_rule (
    id            INTEGER PRIMARY KEY,
    catalog_id    TEXT NOT NULL,          -- 空 = 全局
    timezone      TEXT NOT NULL DEFAULT 'Asia/Shanghai',
    days          TEXT NOT NULL DEFAULT 'all', -- all | mon-fri | sat,sun
    start_minute  INTEGER NOT NULL,        -- 0..1439
    end_minute    INTEGER NOT NULL,
    mult          REAL NOT NULL
);

-- 站点倍率：一个实例的默认倍率 + 可选的逐模型覆盖。同样带版本。
CREATE TABLE vendor_price (
    instance_id   TEXT NOT NULL,
    model_pattern TEXT NOT NULL DEFAULT '*',  -- 精确名或 fnmatch
    effective_from INTEGER NOT NULL,
    catalog_id    TEXT NOT NULL,
    multiplier    REAL NOT NULL DEFAULT 1,
    PRIMARY KEY (instance_id, model_pattern, effective_from)
);

CREATE TABLE meta (key TEXT PRIMARY KEY, value TEXT);  -- schema_version 等
```

容量估算：2 家 × 5 模型 × 4 入口 × 96 桶/天 × 180 天 ≈ 69 万行（上下文档位通常只有 1–2 个非空，实际约 20–40 万行），SQLite 约 30–60 MB，查询仍是毫秒级。保留策略默认「永久」，可在设置里把 180 天前的数据折叠成日粒度（本期不做）。

### 3.3 写入路径（关键性能决策）

**绝不在请求线程里碰磁盘。**

```
请求线程: state.record_usage(...)   →  内存中的 (桶, 维度) 累加
后台线程: 每 5 秒把脏桶 upsert 进 SQLite（一条事务批量写）
进程退出: 再刷一次
```

- 每个 Worker 只写自己 `instance_id` 的行，主键不冲突。
- 写入失败（磁盘满、DB 锁）→ 保留在内存，下个周期重试；日志 WARNING，不影响代理。
- 进程被强杀最多丢 5 秒数据，可接受。

### 3.4 重启与停机

- Worker 重启：内存清空，但 SQLite 里的历史还在。面板按 `ts` 聚合，天然连续。
- 实例停机：数据已在库中，无需读取本地文件。
- **不需要**之前的 `usage.json` 持久化方案 —— SQLite 就是持久层。（现有代码里刚加的 JSON 台账会在实施时替换掉。）

## 4. 计费模型

### 4.1 三层结构

```
标准价目表 (price_catalog)           ← 只维护一份，例如 Claude Opus 5 = $5/$25
        ×
站点倍率 (vendor_price, instance)    ← 每家中转填一个倍率，例如 0.35
        ×
条件修正 (上下文分档 × 时段规则)      ← 只对需要的模型配置
        =
本实例本模型的实际单价
```

这样你的操作是：
1. 新建实例 `aiaimax-gpt`、`waw-deepseek`，填站点倍率 0.35 / 0.28；
2. 把两家的模型名映射到同一个规范模型（`gpt-6.1-sol → gpt-5.5`，`deepseek-v4.1-flash → deepseek-v4`）；
3. 之后新增模型只需加一条「模型映射」，不用重复填价。

### 4.2 「按当时价」还是「按现价」—— 价格是带版本的，不是逐条改

先澄清一个误解：**价格从来不是按请求改的，也不是按天改的**。你能改的只有三类东西：

1. 规范模型的**标准价**（`claude-opus-5 = $5/$25`）；
2. 某个中转实例的**倍率**（`aiaimax = 0.35`）；
3. 分档 / 时段规则。

改价时**追加一条带 `effective_from` 的新版本**，旧版本保留。于是同一份用量数据可以有两种看法：

| 口径 | 用什么价格 | 用途 |
|---|---|---|
| **按当时价**（默认） | 每个桶用「请求发生时刻生效的价格」 | 真实账单：改价不会让上个月的花费变样 |
| **按现价**（切换按钮） | 全部用最新价格 | 模拟：把倍率改一改，看「换这家会花多少」 |

面板上一个下拉就能切：`成本口径：按当时价 / 按现价`。这就是你问的「日后能不能改单价重算」—— 能，而且两种都能看。

### 4.3 成本计算

```
prompt_tokens = input + cache_read + cache_write        # 本次请求的上下文规模
tier          = 满足 min_prompt 的最高档（由 prompt_class 决定）
time_mult     = 命中时段规则的倍率（按桶的起始时间）
unit(x)       = price(x, 口径) × vendor.mult × tier.mult(x) × time_mult

cost = input×unit(input)
     + output×unit(output)
     + cache_read×unit(cache_read)
     + cache_write_5m×unit(cache_write_5m)
     + cache_write_1h×unit(cache_write_1h)
```

### 4.4 三个特殊场景怎么落

| 场景 | 实现 |
|---|---|
| **上下文分档**（超过 200k 涨价） | **不近似**。每条请求自己就能算出上下文规模（`input + cache_read + cache_write`），写入时落进 6 个档位之一（`0-32k / 32-128k / 128-200k / 200-400k / 400k-1M / ≥1M`），档位是桶主键的一部分。所以 15 分钟内同时开多个窗口、上下文长短不齐，也各记各的，不会混。分档边界与常见厂商一致（200k 是边界），因此是精确的；只有你把阈值设成 150k 这种非标准值时，才会落到相邻档，面板会提示。 |
| **时段不同价**（DeepSeek 夜间 5 折） | `price_time_rule`；按 15 分钟桶的**起始时间**判断。规则边界在 :00/:30 时误差为 0。 |
| **缓存 5 分钟 vs 1 小时** | 按下面的优先级判断（见 4.5）。核心思路：**请求里就带着 TTL**，不必猜响应。 |

### 4.5 缓存 TTL 怎么确定（诚实的优先级）

先把「能看见什么」说清楚，这是本设计最容易想当然的地方：

| 信息 | ccc 能否看到 | 说明 |
|---|---|---|
| 客户端请求里的 `cache_control.ttl` | ✅ | 转换前就在 `anthropic_params` 里 |
| 上游返回的 cache read / write token 数 | ✅ | 在响应的 `usage` 里 |
| **上游实际用了哪种 TTL 的缓存** | ❌ | 只有 Anthropic 原生会回拆分；OpenAI 兼容中转不回 |
| **模型内部是否真的命中缓存** | ❌ | 任何网关都看不到，只能信上游上报的数字 |

关键点：**转成 OpenAI 协议时 `cache_control` 不会继续传给上游**（OpenAI 没有这个字段），中转用的是它自己的隐式前缀缓存，TTL 由中转决定，而不是由 Claude Code 请求的那个值决定。所以请求侧的 `ttl` 只能算「客户端原本的要求」，**不能当作实际计费依据**。

判断优先级（从可信到兜底）：

| 顺序 | 来源 | 可信度 | 用途 |
|---|---|---|---|
| 1 | 响应里的拆分：`cache_creation.ephemeral_5m_input_tokens` / `ephemeral_1h_input_tokens`（仅 Anthropic 原生或明确支持的上游） | 精确 | 计费 + 展示 |
| 2 | **实例设置「上游缓存 TTL」**（5m / 1h，默认 5m）—— 你最清楚自己的中转 | 用户声明，稳定 | **计费主依据** |
| 3 | 请求里的 `cache_control.ttl` | 只能当提示 | 面板上标注「客户端请求了 1h」，不参与计费 |

- 每条记录的 TTL 来源记到 `ttl_source`（`response` / `config` / `request_hint`），依赖第 2、3 级的 token 额外计入 `cache_write_est`，面板打「估算」标记。
- 一次内存遍历即可拿到请求侧提示，微秒级，无额外 IO；但它**不改变计费结论**。
- **不采用「统一按最高档 1h」**：对 5 分钟缓存会高估约 60% 的缓存写入成本，误差比标注估算更糟。
- 若某天接入 Anthropic 原生上游，第 1 级自动接管，无需改数据结构。

### 4.6 币种

标准价用 **USD / 1M tokens**（中转行业的通用口径）。面板可切换显示 CNY，汇率是一个可配置的全局值，仅影响展示。

## 5. 「哪家更便宜」怎么算 / 怎么比

单纯看「输入单价 × 倍率」会得出错误结论，因为：

- 输出单价通常是输入的 4–5 倍，输出长得多的站点更贵；
- 缓存命中率高的站点，实际输入成本可能只有标称的 20%；
- 上下文分档可能让大请求翻倍。

所以对比页给这 5 个指标：

| 指标 | 公式 | 回答什么 |
|---|---|---|
| 缓存率 | `cache_read / (input + cache_read + cache_write)` | 前缀利用率 |
| 每请求输入 | `(input+cache_read+cache_write) / requests` | 上下文规模 |
| 每请求输出 | `output / requests` | 是否「多话」 |
| 每请求成本 | `cost / requests` | **真实贵不贵** |
| 有效倍率 | `实际成本 / 按标准价成本` | 与标称倍率的偏差 |

「倍率低但更贵」在散点图上一眼可见：x = 缓存率、y = 每请求成本、点大小 = 请求量。倍率低的那家如果点落在上方，就是输在输出量或缓存率上。

## 6. 图表设计（画什么、为什么）

总览页：

| 图 | 类型 | 数据 | 为什么需要 |
|---|---|---|---|
| 用量趋势 | **折线（堆叠面积）** | 按天/小时的 输入 / 输出 / 缓存读 / 缓存写 | 看趋势与异常尖峰，R1 |
| 构成占比 | **饼图 / 环形** | 所选范围内四类 token 占比 | 一眼看出缓存是否生效 |
| 配置对比 | **分组条形** | 各实例的 token 总量或成本 | R2，哪家吃得多 |
| 模型分布 | **条形（横向）** | 各模型 token / 成本 | 找出最烧钱的模型 |
| KPI 卡片 | 数字 | 请求、输入、输出、缓存读、缓存写、缓存率、估算成本 | 首屏结论 |

对比页：

| 图 | 类型 | 用途 |
|---|---|---|
| 每日缓存率 | **多折线** | 两家的缓存策略差异随时间的稳定性 |
| 每请求成本 | **分组条形** | 同一模型、不同实例的直接对比 |
| 成本 vs 缓存率 | **散点** | 回答「贵在哪」 |
| 对比表 | 表格 + Δ% | 精确数字，可排序 |

价格设置页：只有表单与表格，不需要图表。

不做的图：桑基图（信息密度低）、热力图（请求量不够密时是噪点）。

## 7. 页面与信息架构

```
侧边栏新增「用量统计」
├── /usage            总览（KPI + 趋势 + 占比 + 配置/模型条形）
```

时间范围控件统一：`今天 / 近 7 天 / 近 30 天 / 近 90 天 / 近 180 天 / 自定义`，另加「按小时 / 按天」粒度切换（> 7 天默认按天）。

## 9. 余额 / 额度探测（可选，尽力而为）

中转站没有统一接口，做**适配器 + 自定义**两层：

1. 预设：one-api / new-api 系（`GET /api/user/self`，带 `Authorization` 或 `New-Api-User`）、OpenAI 系（`/dashboard/billing/credit_grants`）。
2. 自定义：`{url, method, headers, json_path}`，`json_path` 形如 `data.quota`，直接取数字。
3. 探测失败不报错，面板显示「未配置/不支持」。

放在阶段 4，不影响主功能。

## 10. 技术选型

| 项 | 选择 | 理由 |
|---|---|---|
| 存储 | **SQLite**（stdlib `sqlite3`） | 零依赖、支持范围聚合、WAL 并发读 |
| 写入 | Worker 内存累加 + 5s 批量 upsert | 热路径零磁盘 IO |
| 后端 | Manager 的 FastAPI 路由直接查 SQLite | 数据量小，不需要额外服务 |
| 图表 | **Chart.js**（单文件 UMD，约 200KB） | 无需构建步骤，和现有 Jinja2+Alpine 风格一致；**本地 vendored**，避免 CDN 在离线/墙内失效 |
| 前端 | Alpine.js + 原生 fetch | 沿用现有页面 |

> 现状：`base.html` 目前用 CDN 加载 Tailwind/Alpine。图表库建议放进 `src/cc_convert/web/static/vendor/` 并由 `app.mount("/static", ...)` 提供，避免面板在断网时变空白。

| 阶段 | 内容 | 验收 |

## 12. 风险与取舍

1. **中转不报 usage**：流式请求最常见。面板必须显示「未上报」计数，否则数字会悄悄偏小。
2. **缓存 TTL 无法区分**：多数中转只给一个 `cache_write`，只能按实例设置默认值计；上游返回精确拆分时才自动使用。
3. **SQLite 与多进程**：WAL + busy_timeout 足够；若未来单机跑几十个实例，再考虑写入队列。
4. **不要记录正文**：只存计数，避免 token 之外的数据落盘。
5. **档位边界是固定枚举**：自定义阈值（如 150k）会落到相邻档位，属于产品上的近似；面板会提示「该模型阈值不在标准档位上」。标准阈值（32k/128k/200k/400k/1M）则精确。

## 13. 已确认的决定

| 决定 | 结论 |
|---|---|
| 成本口径 | **带版本的价格**：默认按当时价，另提供「按现价」开关用于模拟换站 |
| 分档精度 | **不按平均值近似**：把上下文档位作为桶主键的一部分，长短请求各记各的 |
| 缓存 TTL | **请求侧优先**：响应有拆分用响应；否则读请求里的 `cache_control.ttl`；两者都没有才用实例默认值，并记入 `cache_write_est` |
| 图表库 | **本地 vendored**（下载 Chart.js 到仓库，离线可用） |
