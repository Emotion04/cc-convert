# CC Convert 使用规范

本文是 CC Convert 的权威使用说明。**首次使用请从头读到「配置 API Key」一节**，其余按需查阅。

---

## 1. 这是什么

CC Convert 是一座**协议桥**：让只会说 Anthropic 协议的客户端（Claude Code、Anthropic SDK）用上只会说 OpenAI 协议的后端（vLLM、SGLang、各类云 API）。

```
Claude Code ──(Anthropic 协议)──> CC Convert 本地地址:端口 ──(OpenAI 协议)──> 上游
                                          ▲
                              你在 Dashboard 里填上游 URL + API Key
```

完整流程只有三步：

1. 在 Dashboard 里填**上游 URL 和 API Key**
2. 拿到一个**本地地址:端口**
3. 把 Claude Code 指向这个地址

---

## 2. ⚠️ 两个端口（最容易搞错的地方，务必先读）

本机会出现**两个**端口，用途完全不同：

| 端口 | 是什么 | Claude Code 应该连哪个 |
|------|--------|------------------------|
| **18400**（起始） | **Manager** —— 只提供 Dashboard 管理界面 | ❌ **不要连这里** |
| **18401**（起始） | **实例 Worker** —— 真正做协议转换的进程 | ✅ **连这个** |

两端都从上述数字起**顺序寻找第一个空闲端口**，因此实际值可能不是 18400 / 18401。以 Dashboard 或 `ccconvert status` 显示的为准。

**正确做法**：在 Dashboard 的实例卡片上点「**复制配置**」，它给出的就是实例端口，直接粘贴即可。

> **最常见的故障**：把 `ANTHROPIC_BASE_URL` 指向了 18400（Manager）。表现是 Claude Code 报错，或收到一页 Dashboard 的 HTML —— 因为 Manager 根本不处理协议转换。

---

## 3. 前置条件

- **Python ≥ 3.12**（`pyproject.toml` 的 `requires-python`）
- **uv**（源码运行方式需要；如果你是从 PyPI 安装的正式版，见下方「不用 uv 的安装方式」）
- **Git**（仅源码运行时需要）

安装 uv：

```powershell
# Windows (PowerShell)
powershell -c "irm https://astral.sh/uv/install.ps1 | iex"
```

```bash
# macOS / Linux
curl -LsSf https://astral.sh/uv/install.sh | sh
```

安装后**请重开终端**，让 PATH 生效。

### 不用 uv 的安装方式

uv 只在**源码开发**时需要。普通用户直接从 PyPI 安装即可，无需 uv：

```bash
pip install cc-convert
ccconvert start
```

## 4. 首次运行（源码运行 — 推荐）

```bash
git clone https://github.com/Emotion04/cc-convert.git
cd cc-convert
uv sync
uv run ccconvert start
```

逐条说明：

- `uv sync` —— 在项目目录下创建 `.venv` 并装齐依赖（含测试依赖）。依赖版本由 `uv.lock` 锁定，因此在任何机器上结果一致。
- `uv run ccconvert start` —— 无需手动 `activate`，`uv run` 会自动使用项目内的 `.venv`。

> **为什么先单独跑 `uv sync`？**
> 也可以直接 `uv run`（它会隐式同步），但分开执行能让网络或权限问题在**报错信息清晰的位置**暴露出来，而不是淹没在启动过程的输出里。

启动成功后会打印 Dashboard 地址，形如 `http://127.0.0.1:18400`。

### Windows 一键启动

双击 `start.bat`，或右键 `start.ps1` → **使用 PowerShell 运行**。

两个脚本都会先切换到自身所在目录，因此在任何位置调用都可以。若 PowerShell 因执行策略拒绝运行：

```powershell
powershell -ExecutionPolicy Bypass -File start.ps1
```

> **两个脚本行为一致**：都调用 `ccconvert start`，它是**幂等**的。
> 已在运行时只打印当前地址并返回成功，**不会重启**，因此不会打断正在进行的请求。需要真正重启请手动执行 `uv run ccconvert restart`。

## 5. 配置文件与数据目录

| 内容 | Windows | macOS / Linux |
|------|---------|---------------|
| 配置 | `%USERPROFILE%\.ccconvert\config.toml` | `~/.ccconvert/config.toml` |
| 运行时数据 | `%LOCALAPPDATA%\ccconvert\` | `~/.local/share/ccconvert/` |

- 配置文件在**首次启动时自动创建**，通常无需手改。
- 运行时数据包括 `manager.pid`、`manager.json`、`manager.log`、`instances/`。

两个目录都可用环境变量覆盖：

| 变量 | 作用 |
|------|------|
| `CCCONVERT_CONFIG_DIR` | 覆盖配置目录 |
| `CCCONVERT_RUNTIME_DIR` | 覆盖运行时数据目录 |

> **建议只通过 Dashboard 管理实例。** 直接编辑 `config.toml` 虽然可行，但面板写入时会整体重写该文件。

日志文件（`server.log`、`api.log`）位于**运行时目录下的 `logs/`**，即：

| | 日志路径 |
|---|---|
| Windows | `%LOCALAPPDATA%\ccconvert\logs\` |
| macOS / Linux | `~/.local/share/ccconvert/logs/` |

因此 `CCCONVERT_RUNTIME_DIR` 会连同日志一起迁移；Manager 自身的日志在运行时目录根部的 `manager.log`。

## 6. 配置 API Key（黄金路径）

1. `uv run ccconvert start`，浏览器会自动打开 Dashboard（否则 `uv run ccconvert open`）
2. 点击「**添加实例**」
3. 填写：
   - **上游 URL** —— 例如 `https://api.openai.com/v1` 或你的 vLLM/SGLang 地址
   - **上游 API Key**
   - （可选）**目标模型** —— 留空表示透传 Claude Code 发来的模型名
4. 保存 —— 实例会自动启动，监听一个 18401 起的端口
5. 在实例卡片点「**复制配置**」，按你的终端选择 PowerShell / CMD / Bash 格式
6. **重启 Claude Code**

复制出来的内容形如：

```bash
export ANTHROPIC_BASE_URL="http://127.0.0.1:18401"   # ← 实例端口，不是 18400
export ANTHROPIC_AUTH_TOKEN="local"
```

> `ANTHROPIC_AUTH_TOKEN` 填 `local` 是**正常的**：真正的上游密钥保存在实例配置里，由 Manager 通过 **stdin** 传给 Worker 进程，不会出现在命令行参数或环境变量中，也不会写进日志。

## 7. 命令行

源码运行时，以下命令前都加 `uv run`。

| 命令 | 说明 |
|------|------|
| `ccconvert start [--port N]` | 确保 Manager 运行（已在运行则直接返回成功，不重启） |
| `ccconvert stop [-f/--force]` | 停止 Manager（`-f` 强制） |
| `ccconvert restart [--port N]` | **强制**重启 Manager（会停止所有实例，再按 `auto_start` 拉起；会中断进行中的请求） |
| `ccconvert status` | 查看 Manager 与各实例状态 |
| `ccconvert logs [-f] [-n N]` | 查看日志（`-f` 跟随输出，`-n` 指定行数，默认 50） |
| `ccconvert open [--port N]` | 浏览器打开 Dashboard |
| `ccconvert --version` | 显示版本 |
| `ccconvert`（无参数） | 显示帮助 |

## 9. 打包版（绿色 exe，可选）

不想安装 Python / uv 时，可以用打包版。

### 构建

```bat
build_exe.bat
```

或手动：

```bash
uv sync --group build
uv run pyinstaller ccconvert.spec --noconfirm --clean
```

产物在 `dist\ccconvert\`，约 40 MB。**分发时必须拷贝整个文件夹**，只拷 `ccconvert.exe` 无法运行。

采用 onedir 而非单文件：每个代理实例都是一个子进程，单文件版每次启动实例都要重新解压，慢 1–3 秒。

### 使用

```bat
ccconvert.exe start
ccconvert.exe status
ccconvert.exe open
ccconvert.exe stop -f
```

命令与源码版完全一致。

### 与源码版共享数据

两者读写同一份 `~/.ccconvert/config.toml` 和运行时目录，实例配置与状态完全共享。

**同一时间只会有一个 Manager。** 无论哪一边已在运行，另一边执行 `start` 都会识别并提示：

```
Manager already running (PID 40864, python.exe), nothing to do
Dashboard: http://127.0.0.1:18400
  Waw: running (port 18402)

An existing manager is already serving requests. Run 'ccconvert restart' to replace it with this one.
```

进程名可判断来源：`python.exe` = 源码版，`ccconvert.exe` = 打包版。想切换实现时执行 `restart`。

> ⚠️ 不要长期混用两个版本：exe 是构建时的代码快照。每次大更新后重新构建即可。

## 10. 运行测试

```bash
uv sync          # 确保 dev 依赖齐全
uv run pytest
```

**请从仓库根目录运行**（`pyproject.toml` 中的 `testpaths` 已把范围限定为 `tests/`，直接 `uv run pytest` 即可）。

> **测试是沙箱化的。** `tests/conftest.py` 会把 `CCCONVERT_CONFIG_DIR` 和 `CCCONVERT_RUNTIME_DIR` 指向临时目录，并在会话结束时校验你真实的 `~/.ccconvert/config.toml` 未被改动。若某个测试越界，整个会话会失败并明确报出。

运行单个文件：`uv run pytest tests/test_router.py -v`

## 11. 故障排查

**`ccconvert: command not found` / `'ccconvert' 不是内部或外部命令`**
你没有在仓库根目录使用 `uv run`。正确写法是 `uv run ccconvert start`（`uv run` 需要能读到 `pyproject.toml`）。若已 `pip install cc-convert`，则全局命令可用。

**打不开 `127.0.0.1:19500`**
19500 只是测试夹具里的端口，**产品默认不用它**。真实端口是 18400 起，启动时打印。用 `uv run ccconvert status` 查看实际端口。

**Claude Code 连不上**
99% 是端口选错了 —— 检查 `ANTHROPIC_BASE_URL` 用的是**实例端口**（18401+）而不是 Manager 端口（18400）。用 Dashboard 的「复制配置」避免手输。

**实例启动失败 / 端口被占用**
`uv run ccconvert status` 查看状态；或在 Dashboard 的端口页面重新绑定端口。

**异步测试无法收集（`async def functions are not natively supported`）**
开发环境不完整，`pytest-asyncio` 没装上。执行 `uv sync`（不是 `uv sync --extra dev`）。

**配置被"重置"了**
早期版本存在一个真实缺陷：配置存储读取的环境变量名是 `CC Convert_CONFIG_DIR`（名字里带空格），因此文档承诺的 `CCCONVERT_CONFIG_DIR` 覆盖完全失效。该问题已修复。若你在此前版本遭遇过，配置是被运行测试覆盖的（无备份），需要重新在 Dashboard 里添加实例。

**Windows 下删不掉日志目录 / Manager 重启失败**
同样是已修复的历史缺陷：`setup_logging` 丢弃日志 handler 而不关闭，导致文件句柄泄漏、日志目录无法删除或轮转。

**Manager 启动后实例显示 stopped**
通常是上游配置不完整（比如 API Key 为空），或实例端口被占用。查看该实例的日志：Dashboard → 实例 → 日志，或 `%LOCALAPPDATA%\ccconvert\instances\<id>\`。

**想跑多套隔离的配置**
同时设置 `CCCONVERT_CONFIG_DIR` 和 `CCCONVERT_RUNTIME_DIR` 指向不同目录即可。

## 12. 未验证 / 不支持

**Docker 路径在当前版本未经验证。** 仓库内虽有 `Dockerfile` 与 `docker-compose.yml`，但已知存在问题（镜像无 `CMD`，entrypoint 默认执行裸 `ccconvert` 会打印帮助后退出；端口约定 8080 与实际默认 18400 不一致）。请以本文的源码运行方式为准。
